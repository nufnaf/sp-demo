## 建议优先顺序

1. **对固定 JD 任务跳过通用 HTML 设计规范。** 当前不需要模型设计版式，仍发送配色、图表、响应式、打印等要求，还要靠 JD 合同说明优先级。普通报告和其他工作台仍保留通用规范。
2. **让发布交接只加载分派所需的指令和工具。** 它目前走普通任务启动路径，因此虽然只需要委派 browser_task，仍加载通用写作/文件/HTML 能力。保留主 Agent 真实委派，保留文件引用、停止和核对边界，不变成程序直接假装完成。
3. **合并重复的派发和 JD 规则。** 主 Agent 保留路由、用户线索、授权和短回复规则；具体文件格式、正文长度与保存方法由 JD 后台的单一规则来源负责。工具仍保留实际长度校验。不要把内部要求加到观众可见的快捷输入里。
4. **简化浏览器返回给主 Agent 的结果。** `browser_task` 当前把整个 BrowserTaskState 同时作为模型可见 JSON 和 UI details 返回，其中包含完整任务（发布时含 JD）、计时、启动记录和内部路径。可向模型仅返回状态、经核对结果和具体阻碍，完整状态继续留在 UI details/审计。这主要降低操作完成后的总结输入，并不能缩短之前的网页填写。

浏览器的页面不可信、使用最新元素引用、批量操作后读取新状态、禁止重复提交、完成前核实、停止/关闭页与授权边界应保留。它的专用指令本身已经较短，不建议作为本轮主要压缩目标。

## 延迟判断

JD 正文生成请求约 80% 输入已命中缓存，模型仍输出 1173 / 906 tokens；从飞书返回到保存指令耗时为 23.351 / 17.750 秒。因此输入精简有价值，但当前证据不能证明长提示词是主要瓶颈，也不能推出提示词减半就会总耗时减半。

OpenAI 官方指出，通常输入 token 减半可能只带来约 1–5% 延迟改善；巨大上下文可能不同。此数字是一般指导，不是 Luna 或本 App 的保证。来源：[Latency optimization — Use fewer input tokens](https://developers.openai.com/api/docs/guides/latency-optimization#use-fewer-input-tokens)。

下一次验证应分别记录主 Agent 派发、JD 后台、发布交接与浏览器模型的输入/缓存/输出 token 和耗时；使用相同正文预算，避免混入正文长度变化。优先去掉无关规则和重复输出，再比较真实端到端结果。
