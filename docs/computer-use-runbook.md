# 飞书日程操作手册与模型实测

2026-09-11，工作树 `computer-use-desktops`。实现第一层操作手册，并修正实测发现的原生输入与核验问题；没有增加组合工具、自动代填、固定坐标或 API 写入回退。

## 实现

`electron/computer-use/calendar-runbook.mjs` 为正式 `calendar-agent.mjs` 和开发草稿验收脚本提供同一份流程知识。模型仍逐次调用现有原子工具。

流程覆盖新建编辑器、选择目标日历、标题/日期、时间的双击编辑与失焦提交、说明的可见区域与渲染核验、最终核验。重点是复用动作返回的当前 AX 状态、跳过已经正确的字段、避免重复观察，以及只在像素定位或不确定状态下请求截图。所有窗口、控件 token 和坐标继续来自实时观察。

正式任务仍强制选择指定日历，无法选择时停止；只有原有受控提交工具能保存。草稿验收明确禁止保存。目前正式任务和草稿验收均要求目标日历准确匹配；下文早期对照样本允许在默认日历填写未保存草稿，因此不能把它们算作目标日历写入成功。

## 日历身份诊断

本轮只读 API 确认：开发配置与已安装 Syntropic 使用同一应用、同一目标日历；「Syntropic 演示日历」类型为 `shared`，应用当前角色为 `owner`。机器人信息接口确认其名称为「星流科技」，ACL 中的 owner ID 与该 Bot ID 一致。

ACL 另有一个非 Bot 的 `reader` 成员；其姓名查询被通讯录权限拒绝，本轮没有扩大权限。此前客户端直接观察到刘星为该日历的订阅者，且本轮编辑器依旧只能使用刘星个人日历。不能把应用身份的 owner 等同于客户端账号拥有编辑权限。

早期日程功能通过 tenant_access_token，以 Bot 身份访问配置的专用日历，便于演示预设和归属事件的初始化/清理。Computer Use 本身不要求共享日历；如改用个人日历，应同时调整 GUI 目标、API 读取核验及演示重置的范围。这一初次诊断没有修改日历权限或目标配置；后续进展见下节。

规则依据：[查询日历信息](https://open.feishu.cn/document/server-docs/calendar-v4/calendar/get.md)、[获取访问控制列表](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-acl/list.md)、[获取机器人信息](https://open.feishu.cn/document/client-docs/bot-v3/obtain-bot-info.md)。本机脱敏结果为 `runbook-20260911/calendar-access.json`。

## 个人日历适配与授权（2026-09-11 后续）

官方 [创建日程](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/create) 支持应用或用户身份，目标类型为 `primary` 或 `shared`，调用者须为 `writer` 或 `owner`。[创建访问控制](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-acl/create) 要求调用者已是目标日历 `owner`。应用创建者不是 Bot 的执行身份；开通 API scope 不等于获得某个日历的 ACL。

通过已知共享日历成员查询到一个用户主日历，Bot 目前角色为 `free_busy_reader`，API 标题为“用户517466”。客户端显示的个人日历名称为“刘星（星流科技HR）”。授权后必须以刘星用户身份查询主日历、确认 ID 对应关系，再切换配置，不能只根据名称猜测。

已为现有“星流科技”应用开通两项免审用户权限：`calendar:calendar:read`（核对本人主日历）和 `calendar:calendar.acl:create`（为 Bot 添加编辑权限）。开发者后台已显示这两项为用户身份、已开通。为 CLI 增加 `syntropic-calendar` 配置档，复用现有应用，未创建新应用。刘星已完成用户授权，已核对本人主日历和候选 calendar_id 一致、用户角色为 owner。已用该用户身份成功给当前 Bot 创建 writer ACL；随后以 Bot 身份查询到 primary/writer，且应用日程读取通过。

授权与切换的验证顺序（现已完成；第 4 步覆盖卡片数据接口，未重测前端渲染）：

1. 确认用户身份与本人主日历，再以该 owner 的用户身份向主日历添加 Bot 的 `writer` ACL。ACL 请求使用 `scope.type=user` 与本应用的 Bot open_id；文档没有专门说明 Bot 作为被授权成员的案例；本机接口已实际返回成功，Bot 再次查询也确认 writer。
2. 用 Bot 的 tenant token 查询同一 calendar_id，要求返回 `writer`；再验证日程读取。若 ACL 不接受 Bot，评估将日历 API 改为已授权用户身份，不创建另一个共享日历，也不让 Bot 自行提权。
3. 在本工作树私有配置设置 `calendarId` 与完整 GUI 名称 `calendarName`，移除旧日历的 `calendarResetEventIds`，核对重置仅处理归属标记事件。既有请求与重置记录按 appId/calendarId 隔离。旧共享日历数据保留。
4. 验证个人日历 GUI 保存、Bot API 读取核验和卡片同步；仅清理这次有归属标记的测试事件，不添加参会人。完成前不能宣称个人日历已切换成功。

代码适配：GUI 目标名现在来自 `FeishuDemoClient.calendar().calendarName`，不再写死共享日历；缺少名称时在输入前报错。AX 核验允许同一个个人姓名重复出现在右侧忙闲栏，但仍拒绝未选中的列表项和无法确定来源的重复名称。手册要求已经选中目标时跳过选择器，限制失败后的探索，并删除基础提示词中重复的操作步骤。没有引入第二层组合工具。

草稿验收需显式提供 `COMPUTER_CALENDAR_NAME`；最终核验会检查选中日历，不再悄悄改用默认日历。手册唯一生产注入点是独立的原生 `calendar-agent.mjs`，另一使用处是手动运行的草稿脚本；没有全局 prompt/skill 注入。新增隔离检查覆盖 app/lib/electron/scripts 的手册引用，Browser Task 的会话结束行为也复验通过。

本次 70 项针对性测试及 TypeScript 检查通过，修改文件 ESLint 无错误（原有未使用参数警告 1 项）。新增覆盖包括个人名称重复、API/GUI 配置一致、未配置时不操作、手册注入范围和日历重置边界。这次代码检查时个人日历版尚未重测。授权完成后的实际保存与性能结果见下一节；未替换已安装 App。

完整测试暴露并修复了两处问题：

- 多行说明在 AX 中是同一编辑器下的多个可见文本节点。核验器原先要求单个节点包含整段文字，导致误判。现仅聚合同一说明编辑器内、具有实际可见几何信息的文本，拒绝缺段或额外内容，不信任隐藏 AXValue。

前两轮不能算成功：第一轮因多段核验误判在 242.873 秒、32 次调用时停止，未保存；第二轮 20 次调用后 GUI 保存，但 API 检查发现说明不完整，136.105 秒后正确报告失败。两轮均未添加参会人；第一轮草稿随后退出，第二轮仅清理了精确识别的测试事件。输入实验事件也已通过 Bot API 删除并确认不存在。未运行个人日历全量重置。

## 第二层组合字段优化（2026-09-11 后续）

本节接续上述历史记录。桌面与预览 UI 调整后，仍沿用同一原生执行、Pi 模型与 API 核验链路；本轮开始加入已对齐的第二层工具，未修改 Browser Use、桌面 UI 或已安装 App。

- `computer_step` 可用 `screenshot:true` 随动作结果返回新截图。点击创建时的 `waitForEditor:true` 有界等待并选择本次新增的唯一空白日程窗口；AX 尚未就绪时只继续观察，不再点击创建。已有草稿、多窗口歧义、切换到其他编辑器都拒绝。
- `computer_edit_field` 只接受 `startTime`、`endTime`、`description` 和本次请求的准确值。时间内部执行双击、写入、失焦、检查 AXStaticText，返回两个时间供模型跳过已联动正确的结束时间。说明内部在左侧表单有限滚动、展开、写入全文，再点击当前界面中两枚会议纪要按钮之间的中性文字完成失焦，检查完整可见内容。
- 所有坐标来自当前 AX 控件和当前截图，不保存固定坐标、窗口 ID 或 token。纯 AX 返回没有截图几何时，可见性使用该 AX 树的窗口 frame；不能把“没有截图尺寸”当作控件不可见。
- 每个内部动作前重新读取状态，检查暂停、停止、当前编辑器、所选日历及参会人区域。失败返回阶段、已完成动作和新状态，不自动重放剩余动作。单个字段最多四次滚动；每次任务还限制模型调用和原生动作总量。预览队列可以在内部动作之间继续读取画面。
- 保存仍独立使用 `computer_submit`：保存前两次检查、持久化不确定写入边界、单次点击及 Bot API 完整内容核验。组合工具不能保存或邀请参会人。手册增强只由原生生产 agent 显式开启；旧草稿脚本保留与其工具集匹配的第一层手册。

## 后台输入的前台点击失灵回归（2026-09-11）

在 Cua 0.26.1 上复现：后台原始坐标双击之后，前台 Electron 的 `BrowserWindow.isFocused()` 和 `webContents.isFocused()` 变为 false，但页面 `document.hasFocus()` 仍为 true。连续三次原生鼠标点击均未触发按钮；普通单击命中 AXPress 路径时没有这个现象。单独调用 Electron `focus()` 也未恢复。

根因在 [Cua 的后台点击实现](https://github.com/trycua/cua/blob/b4e3cae/libs/cua-driver/rust/crates/platform-macos/src/input/skylight.rs)：`activate_without_raise` 给前台进程发送失焦记录，但 WindowServer 的前台进程标识没有改变；`click.rs` 仅在观察到飞书变为前台时才执行恢复，因此遗漏前台原生窗口失焦的状态。

适配层为每次后台坐标点击租用一个短生命周期的 `input-focus` 原生辅助进程，在输入实际结束后补齐原生激活、key-window 记录。它不切换系统前台 App、不抬升窗口、不发送全局鼠标/键盘输入。用户切到另一个 App 时放弃旧 App 的恢复；同一 App 换窗口时以当前窗口为准，不拉回旧窗口。AX token 操作和录屏不进入这条路径。中途停止会等待已发出的原生点击完成，然后恢复焦点，不再执行下一步；输入失败和父进程 EOF 也释放租用。缺少保护组件时拒绝坐标操作，避免静默退回已知有问题的路径。

本机验证（证据在 `build/verification/computer-use/focus-20260911/`）：

- `before.json` / `fixed.json`：原生双击前后对照，修复后三轮的下一次真实鼠标点击全部成功。
- `fields.json` / `fields-final.log`：将测试窗口置于前台后，未保存的独立日程草稿完成开始时间、结束时间和两行说明编辑；操作间穿插的 12 次前台真实点击全部通过。草稿已取消并确认退出，没有保存或邀请。
- `switch.json`：中途切到 Finder 保持 Finder 在前台；同一 Electron App 新选窗口保持可用，旧窗口没有被重新选中。
- `desktop.json`：独立 Electron 宿主加载当前 Syntropic 开发界面，在六次飞书后台双击后，以原生鼠标交替打开/关闭桌面总览，六次均通过。
