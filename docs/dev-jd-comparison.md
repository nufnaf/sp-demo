本文是飞书组合读取实施前的对照记录。后续已实现本文提出的合并读取建议，最新代码、安装版与实测边界见 [飞书合并读取验证](feishu-combined-read.md)。

## 版本与测试边界

已先提交当前优化：`aa2f67e`（`feat: streamline JD generation and prewarm browser execution`），未推送。随后核对本地 `dev`、`origin/dev` 及远端 `refs/heads/dev`，均为 `7992aeb02506c8b14052720069c581309f44f29f`。

没有切换分支、创建 worktree 或修改主仓。通过 `git archive dev` 将原代码导出至当前 worktree 的忽略目录，测试直接调用该版本的 `startRpcSession(..., { role: "jarvis" })`，真实经过主 Agent 的 `start_task`、后台 Agent、读资料及写文件。没有替换 dev 的提示词、工具实现或任务分派实现。Node 使用安装包内的 24.20.0；两边 Pi SDK 均为 0.84.3。

这是后台调用链对照，不是 dev 界面和飞书 CLI 的完整端到端验收。为避免触及个人资料和引入 CLI 登录差异，先从专用飞书应用真实读取同一份《星流科技业务介绍》，给 dev 一份原文文件；dev 请求明确资料已经在当前工作目录，只需读取该文件。当前版本仍由 Agent 调用真实飞书列表与正文工具。各轮原文 SHA-256 相同，预先读取原文的时间不计入生成时间。该设置给 dev 省去了联网找资料的工作，不能据此计算严格 A/B 加速百分比。

每轮使用新的临时工作目录和隔离 Pi 配置目录，仅复制所需模型凭据/模型定义，设置指定模型及 low，不加载原会话历史或复制全套个人插件配置。凭据未进入提示词、报告、Git 或日志，轮末随临时目录清理。此环境不复原历史开发者机器的全部配置、缓存或服务状态。

计时起点为向已经创建好的主 Agent 发送请求；终点为成功写出 JD 文件（当前保存工具还会读回核对）。“任务已派出”、最终文字回复、打开文件通知单独看待，不能当作同一个完成点。

## 实测

| dev + Luna，第 1 轮 | 69.354 秒 | 42.804 秒 | Markdown；含一次 WebSocket 错误重试，异常样本 |

原默认模型的服务端错误为：`The 'gpt-5.4-mini' model is not supported when using Codex with a ChatGPT account.` 这是当前账号本次请求的结果，不能据此推断过去不曾正常使用，也不能把 3.6 秒失败当成快速完成。

dev 第 1 轮及 HTML 轮的连接错误包含 `WebSocket error` / `fetch failed`，不纳入正常延迟比较。不能仅凭这些错误归因于 API 高峰期、模型算力或本次 worktree 改动。

当前安装版此前两次真实 UI 全流程 JD 计时为 23.903 / 27.071 秒，详见 [提示词精简验证](prompt-length-audit.md)。与本次后台正常轮次接近；不是本次重新运行了全部招聘网页流程。

## 实现差异与结论

**本次没有复现“dev 比当前更快生成 JD”。** 历史体验无法在原模型当前被拒绝的条件下原样重现，同模型正常样本也不支持回退到 dev 更快。样本少、生成文本不同，不声称当前在任何时段都更快。

dev 已经有真实生成能力：`lib/rpc-manager.ts` 的 `createJarvisTaskRuntime().startTask` 创建真实 AgentSession 并调用 `session.send({ type: "prompt", message })`。当前 worktree 增加的是专用资料读取、招聘场景交付约束与产品衔接，不能说真实 JD 生成是本 worktree 才实现的。

| 项目 | dev | 当前招聘工作台 |
| --- | --- | --- |
| 主 Agent | 通用调度提示；自行写完整任务说明 | 精简调度提示；后台已有规则，少复述 |
| 后台任务 | 通用编码/办公 Agent，多种工具及资源加载 | 招聘专用提示与三个工具；不加载无关技能、项目上下文及通用设计规范 |
| 输出格式 | 用户未指定 HTML 时可选 Markdown；两轮均如此 | 纯文本内容交给固定模板，必定生成 HTML |
| 页面生成 | 要 HTML 时模型输出 HTML/CSS | 模型只生成标题及正文；程序渲染样式 |
| 正文长度 | 没有当前场景的上限 | 目标 900–1100 字符，硬上限 1200 |
| 保存与检查 | 可自行选择 write、read、file_open 等后续步骤 | 一次保存工具写入、读回核对，不再复述全文或重复检查 |

`lib/html-artifact-prompt.ts` 在 dev 和当前版本的 SHA-256 完全相同。dev 没有隐藏的、更短的 JD 专用生成器；当前招聘任务通过 `lib/recruiting-task-profile.ts` 排除了这份通用 HTML 设计提示，普通任务仍沿用它。

正常 dev Markdown 轮：模型写入内容 1504 字符，写文件的模型输出 1092 tokens；读取正文后到 write 用时 24.000 秒。当前两轮：标题、章节标题和正文合计 823 / 845 字符，保存调用所在模型输出 675 / 678 tokens；读取正文后到保存调用为 13.288 / 13.844 秒，第 1 轮实际保存约 9 ms。内容长度和多轮工具决定共同构成差异，不能把全部时间变化归因于系统提示长度。

## 对照时提出的后续优化建议

优先合并飞书“按标题查找 + 读取正文”为一个受限工具，或利用当前打开文档的已验证标识直接读取。在当前第 1 轮中，两次模型决策约 3.829 / 1.747 秒，列表及正文工具约 0.558 / 0.745 秒；而 `FeishuDemoClient.read()` 内部又会做一次授权列表核对。合并可以省一次模型往返及重复检索，同时保留专用应用、允许文档列表与真实读取的边界。不能为了省时跳过授权检查。实际收益需改动后复测，不能直接把所有这些时间都算成可消除的等待。

主 Agent 派发目前仍花约 5 秒。绕过这一次模型调用，直接启动固定 JD 任务，可能进一步减少等待，但属于调度行为改变；本次没有擅自改为固定路由或 mock。正文输出仍是主要正常等待，继续压缩必须与信息完整度一并检查。没有必要恢复 dev 的通用 HTML 生成方式。

连接失败另行保留证据：两版共用同一 Pi 请求实现，先观察是否持续复现，再决定是否调整传输方式；不在此次比较中修改全局 Pi 网络或重试配置。
